# 未来艺术馆扩展设计

## 目标与边界

该模块以“可继续开发的展厅骨架”为目标，而不是把一个固定效果图硬编码成不可维护的页面。三维建筑、展位数据、展品渲染、平面图、访客终端和虚拟操作系统彼此解耦，业务团队可以替换展品和数据，三维团队可以替换建筑资产，界面团队可以扩展虚拟应用，而不必修改其他层的核心逻辑。

展厅采用局部米制坐标。大厅宽 50 米、深 36 米、墙高 8.4 米。48 个展位分布在北墙、南墙、东西侧墙和中央展岛。四个策展区各 12 个展位，展位编号和三维对象使用同一个 `ExhibitConfig.id`，因此三维拾取、平面图、展签、数字展册和镜头导航不会产生第二套映射表。

                        北墙数字艺术区 A：01 ─ 12
       ┌──────────────────────────────────────────────────┐
       │                                                  │
       │ C 区侧墙      D 区中央展岛       C 区侧墙        │
       │ 25 ─ 30    37 38 39 40           31 ─ 36         │
       │            41 42 43 44                           │
       │            45 46 47 48                           │

       │                 访客交互终端                      │

`ExhibitionExperience` 由 React 的动态导入按需加载。园区首屏不需要解析展厅窗口系统和 48 个展位组件。三维画布只负责空间对象，抬头显示界面和虚拟桌面位于普通文档对象模型层；三维墙面大屏与交互终端通过 Drei 的 `Html` 将 React 界面映射进三维空间。

## 展品体系

`ExhibitDisplayKind` 当前包含五类。`painting` 使用墙面画框和纹理或程序化图案；`procedural-sculpture` 使用参数化几何、金属材质和基座；`relic` 使用玻璃展柜、暖色聚光和文物体块；`hologram` 使用透明叠加、旋转线框和发光节点；`imported-model` 使用 `GLTFLoader` 加载本地 GLB。

每件展品同时具备标题、艺术家、年份、策展区、编号、类别、展示类型、位置、朝向、强调色、描述、可选模型和可选图片。界面层只读取这份数据，不直接查询三维对象。点击平面图编号时，状态层保存展品标识并触发相机请求；相机层再按数据位置计算观察点。

导入模型使用 Suspense 边界和可替换占位结构。实际项目中应给模型加载失败增加遥测记录，并为远程资产设置内容哈希和版本清单。模型不应从不受控公共地址直接在生产运行时加载，建议进入自己的对象存储和内容分发网络。

## 建筑与视觉语言

第四版建筑骨架采用高明度白色物理材质与少量共享几何，视觉基调由白色墙面、顶部采光井、黑色轨道灯、浅青导光线和暖色展品重点光组成。地面模拟白色树脂或微水泥，使用受控反射而不是全镜面。后期暗角被压低，场景曝光和雾色被提高，避免界面遮罩把展厅重新压成深色。

环境雾用于柔化远处对比度并隐藏边界。接触阴影只静态计算一次，适用于当前建筑和展品基本不移动的场景。动态访客不依赖实时高分辨率阴影。后期 Bloom、画廊灯光、访客数量、动态媒体屏开关和媒体亮度可由控制坞或墙面虚拟系统调整。

画面层次建议维持以下关系：建筑基础亮度最低，导光线和界面为冷色中高亮，展品重点光局部使用暖色，平面图和窗口界面保持最高信息对比度。不要把所有材质都设置为高发光，否则 Bloom 会吞噬边缘并降低展品辨识度。

## 相机与交互

相机采用 `camera-controls`，而不是自行维护球坐标、阻尼和多点触控。预设包含总览、入口、导航大屏、交互终端和展品聚焦。展品聚焦位置不是硬编码的 48 组镜头，而是由展品位置、朝向、正向向量和侧向偏移实时计算。

```text
展品中心 P
     ▲
     │ target height
     │
     P ─────── front vector ─────── Camera offset
              ＋ side offset
              ＋ vertical offset
```

这种计算允许策展人员移动展位而不必重新录制镜头。若后续加入墙体遮挡或复杂分区，应增加导航网格或预计算相机锚点，不能只依赖直线插值。

## 平面图联动

`ExhibitionFloorPlan` 是大屏、全屏地图和虚拟系统地图应用共享的唯一平面图组件。它接收紧凑模式、交互模式和图例开关，三处界面不会产生不同的展位坐标逻辑。展位三维坐标被映射到二维展厅画布；选中状态、悬停状态和策展区过滤均来自 Zustand。

墙面大屏不是一张烘焙图片。它是可点击的 React 界面，能够实时显示选中展位、客流和设备状态。大屏外壳仍是 Three.js 几何，因此可以接受光照、遮挡和空间透视。

## 虚拟操作系统

虚拟系统在应用层模拟桌面工作流，而不是虚拟机。第四版不再使用全屏覆盖层：系统的 1366 × 768 逻辑桌面由 Drei `Html transform` 映射到中央展墙的实体屏幕表面。`react-rnd` 提供窗口拖动和缩放，状态机管理窗口层级、最小化、最大化和任务栏恢复。每个应用是普通 React 组件，可以访问展厅状态并触发三维场景动作。

设备控制应用直接修改画廊灯光、Bloom、访客数量、展签和建筑显隐；地图应用选择展位并触发相机；数字展册读取同一个展品数据源；日程应用读取展厅日程；浏览器加载本地页面或允许嵌套的外部页面。该结构相当于“桌面壳层 + 领域应用”，不包含文件系统、用户权限、进程隔离或内核能力。

## 性能预算

48 个展位不应等价于 48 套完全独立的大纹理和高模模型。当前版本主要使用程序化几何、共享材质和十八件轻量 GLB，确保学习环境和普通笔记本可以运行。四块动态屏幕使用三段本地循环视频，视频元素在页面隐藏挂载，场景只消费 `VideoTexture`。扩展到真实项目时建议建立明确预算：首屏压缩资源控制在 25 至 40 MB，单件常规展品控制在 20,000 至 80,000 三角形，4K 纹理只用于必须近距离观看的重点展品，重复底座和展柜必须实例化。

虚拟操作系统和大屏界面属于文档对象模型。大量高频图表不应每帧随 Three.js 渲染循环更新。遥测建议按 1 至 5 秒节流，动画只作用于数值变化和必要的状态过渡。关闭虚拟系统时卸载 iframe，避免后台网页继续运行定时器。

## 接入真实业务系统

建议把后端接入分为四类：展品目录来自内容管理系统或数字资产管理系统；设备状态来自楼宇自动化或物联网网关；客流来自摄像机分析或门禁系统；活动日程来自票务或预约系统。前端建立适配器，把它们统一转换为 `ExhibitConfig`、`ExhibitionDevice` 和 `ExhibitionScheduleItem`，三维组件只消费稳定模型。

实时数据通道可使用 WebSocket；低频配置使用 Hypertext Transfer Protocol；设备侧 Message Queuing Telemetry Transport 不建议直接暴露给浏览器，应通过服务端网关完成鉴权、主题过滤和数据聚合。任何控制类动作都需要服务端授权、审计和幂等机制，不能因为虚拟桌面看起来像本地系统就跳过安全边界。
